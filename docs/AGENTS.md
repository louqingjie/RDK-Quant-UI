# docs/AGENTS.md

本文件定义文档的分层、写作规则与篇幅上限。代码、测试、提交的约束在[仓库根 AGENTS.md](../AGENTS.md)，不在这里重复——一个事实只有一个家，复制过去迟早有一份过期。

## 文档结构

作用域由**主题和位置**决定：一份文档详述自己的主题，对子级只用目的、职责和高层行为带过，细节链到拥有它的那份文件。文档类型不改变这个作用域。一份参考可以对自己的主题写全，不能对别人的主题写全。

每份文档归类为**教程**或**参考**。教程是一条有顺序的路径，只引入每一步需要的东西；参考声明一个查找范围、只写当前行为，不排教学顺序。

写之前按这个顺序定：把文档放进树里 → 定它能写到多细 → 选教程还是参考 → 教程按前置依赖排序 → 把属于下级的细节挪走、换成链接。

## 分层：一个事实只有一个家

| 层 | 职责 | 不放什么 |
|---|---|---|
| [README.md](../README.md) | 使用者：装、启、界面、排错 | 架构理由，实测的容器细节 |
| [AGENTS.md](../AGENTS.md) | 改代码的 agent：铁律、流程、踩过的坑 | 使用步骤，长篇教程 |
| [CONTAINER_FINDINGS.md](../tests/fixtures/CONTAINER_FINDINGS.md) | **实测**出的容器行为：格式、默认值、报错原文 | 没实测过的推测 |
| `docs/` | 上面三处放不下、且不属于代码注释的长篇 | 已经有家的任何事实 |
| 代码注释 | 局部契约：行为、失败、时序、所有权、例外 | 推理过程，测试走查，代码复述 |

放置：实测结论 → `CONTAINER_FINDINGS`；踩坑经验 → 根 `AGENTS.md`；怎么用 → `README`；其余且够长 → `docs/`。

`docs/` 现在只有这一份文件。**不要为了"结构完整"往这里搬东西**——上面几处各有明确读者，搬进来只多一次跳转。

## 写作规则

- **写当前状态。** 历史留在提交信息里。正文说清现在的机制，不写"以前是……后来改成……"。引用历史用提交号。
- **说数字，不说形容词。**「快了很多」没用，「169 秒 → 9.26 秒」有用；「数据量大」没用，「3504 张、1474 种分辨率」有用。
- **没验证就标出来。**「测过了」和「应该可以」要能一眼分开。宁写「X3 容器未验证」，也不要写得像验证过。
- **一条规则点出执行它的东西。** 有测试守着的点名测试（比如探针的 3.8 兼容由 `test_containerops.py` 守着），点名前**先去看一眼是不是真在那个文件里**——写错位置比不写更误导；没有执行机制的，直说「靠人看」，不要写得像有门禁。
- **代价要写到能被后人推翻。**「这样做更简洁」不合格；「每次重渲染 SVG，套件 60 秒变 170 秒」合格。后者真的被推翻了——那个代价其实是 bug 造成的。
- **踩过的坑写清三件事**：错在哪、为什么会错、怎么发现的。只写结论，后人不知道边界在哪。

## 篇幅

这个项目没有文档门禁，只有 `pytest`。给个大致参考，超了先看是不是放错了层：

| 文档 | 参考上限 |
|---|---|
| 根 `AGENTS.md`、本文件 | 100–200 行 |
| `README.md` | 不设行数，但要能一口气读完 |
| `CONTAINER_FINDINGS.md` | 每节 ≤ 40 行 |

超了按这个顺序处理：**搬家**（挪到正确的那一层，留一行链接）→ **压缩** → 才考虑放宽。篇幅是护栏，不是裁减目标。

## 废话清单

审任何一份文档时找这些：

- **重复的规则**：搜一句有辨识度的话，只留一个家，其余改成链接。
- **历史写在错误的层里**：正文只写当前事实，历史回它自己的家。
- **状态标注**：「已实现」「待办」这类字眼会烂——仓库结构和测试才是权威。
- **手工复述**：文件树、接口表这类有源头的东西，别抄一份会漂移的副本。
- **推理过程**：怎么一步步想通的、试过哪条死路——留结论和理由，删路径。
- **段落墙**：一段里塞好几条规则，还带一堆括号补充。拆开，或把细节降到它的家。
- **强调通胀**：到处都是加粗，等于没有加粗。只强调会改变行为的那半句。

## 文档和代码相反

这是最该找的一类问题，**比缺文档危险得多**：缺文档只是没人看，写反的文档会把人引向错误的修改。

本项目真实发生过：

> `CONTAINER_FINDINGS.md` 写着「容器**必须**以 `--user` 运行」，
> 而 `runner.py` 里写着「**刻意不传** `--user`」。

**代码是对的。** `hmct/ir/onnx_graph.py` 无条件 `import torch`，torch 在权限 700 的 `/root/.local` 下，传 `--user` 会让 `import torch` 直接失败。

所以：文档和代码冲突时，**先假设代码是对的**（它经过实测），去改文档。反过来做，等于把已经修好的问题重新装回去。改完在提交信息里说明哪一处漂移、为什么。

## 引用

当前文件用相对 Markdown 链接。历史引用用提交号，不用「上次改的时候」。链接指向的文件被移动或改名时，**同一次改动里**把引用一起改掉。

## 怎么判断写得行不行

没有自动检查，靠三个问题：

- 一个**没参与这次改动**的人，照着这篇文档能做成吗？`README` 尤其要过这一关。
- 文档里每个**数字**，是不是都能对应到某次实测？
- 有没有哪句话，和代码里的注释、或者另一份文档，**说的是反的**？
